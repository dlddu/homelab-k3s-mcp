## 판정 기준 — 슬라이스 1~13 의 구분 그대로

1. **본문이 그 주장을 대신 말하면 지운다.** 본문이 *결과*·*무엇*만 적고 주석이 지는 *이유*·*교차 제약*은 적지 않으면 「다른 주장」.
2. **본문이 스스로 주석을 가리키면 원본은 주석 쪽** — 유지. 이 층에서 그 형은 없었다(#78 「AC 포인터는 지우지 않았다」는 정책 자신의 판정 기록이지
   원본 지목이 아니다).
3. **본문이 결론을 담더라도 앞으로의 편집을 구속하는 서 있는 불변식이면 유지**(README 3분 표 둘째 줄). 이 층에서는 **결합**(`genericPairs` 가 서브리소스를
   쌍에 덧붙이는 한 `parseDeleteTarget` 의 거부가 서 있어야 한다), **무엇이 조용히 통과하는가**(사본이 둘이면 갈린다 · 「deleted」 로 고치면 어떤 테스트도
   붉지 않는다 · float64 로 지나가면 큰 정수가 소리 없이 반올림된다), **성립 조건**(apiserver 의 거부는 승인이 소비된 뒤에 온다)이 여기 든다.

이 층에서 새로 확인한 것: **같은 명제의 소유자가 한 패키지의 두 파일에 있고 한쪽 행(#25 `gate.go`)이 이미 ③④ 판정을 마쳐 소유자로 서 있을 때, 다른 행의
문장은 첫째 줄이다** — 슬라이스 10 이 `github.go`↔`commitstatus.go` 에 적용한 것과 같은 형. `parseUpdateTarget` doc 이 「함수가 하나인 이유」와 「게이트 쪽이 먼저
돌아야 하는 이유」를 한 문단에 겹쳐 적었는데, 앞의 것은 이 doc 만의 것이고 뒤의 것은 `updatePairs` doc 의 것이다. 09-15 판정(`rct_20260914-0017`)이 이 11줄을
「가장 복원되지 않는 자리」로 유지했지만 그때는 ①② 만 물었고 `updatePairs` doc 과의 관계는 세지 않았다(슬라이스 8 관찰 ⑵ — 앞 판정의 「유지」는 ①② 한정 진술로
읽는다).

## 항목별 — 제거 3줄

### 제거 ⑴ — `parseUpdateTarget` doc 319–321 의 한 문장 (−2)

```
// One function rather than a copy on each side, because both sides run it: the
// gate runs it before an approval request exists, and the handler runs it again
// after. `docs/test-resource-generic.md` scenario 8 wants a negative or missing
// replicas refused with **no approval request made at all**, and the handler is
// downstream of authorize, so the handler alone cannot deliver that. A second
// copy is how the refusal the operator never saw and the refusal they did stop
// agreeing about what a valid call is.
```
→ 「`docs/test-resource-generic.md` scenario 8 wants … cannot deliver that.」 를 지우고 앞 문장 안에 소유자 포인터 「(updatePairs says why it must)」 를
접는다. 앞뒤 문장은 그대로(7 → 5줄).

**③ #97 「설계 결정 2 — 인자 검증이 게이트보다 앞선다(`updatePairs`). `docs/test-resource-generic.md` 시나리오 8 이 음수·누락 `replicas` 에 대해 「승인
요청조차 만들지 않음」을 기대 결과로 적는데, 핸들러는 `toolsCall` 에서 `authorize` 뒤에 돈다. 게이트보다 이른 유일한 자리가 선언의 쌍 해석이라 거기서
검증한다」** ✅ 축자. 그 위에 **① `internal/mcp/gate.go::updatePairs` doc**(원장 #25, ③④ 판정 완료)이 같은 명제를 「They cannot wait for the handler:
authorize runs before it, so a call the handler would reject has already cost an approval request by then, and scenario 8 asks for a negative or missing
replicas to be refused without one ever being made. Pair resolution is the only thing that runs earlier」로 든다 — 이중 복원. 편집의 실패 모양도 첫째
줄이다: 게이트 쪽 호출을 걷는 편집은 `TestUpdateScaleBounds` 의 「gate calls = 0」 단언을 **붉힌다**(조용히 통과하지 않는다). 남긴 「One function rather
than a copy on each side … A second copy is how the refusal the operator never saw and the refusal they did stop agreeing about what a valid call is」는
다른 명제 — **왜 검증 함수가 하나인가**. 사본을 둘로 가르는 편집은 어떤 테스트도 붉히지 않고 두 거부가 서서히 갈린다(둘째 줄). ③ 어디에도 없고(#97 은
「`updatePairs` 쌍 해석」과 「핸들러」를 따로 적을 뿐 「하나」를 말하지 않는다) `updatePairs` doc 도 이것을 적지 않는다 — 09-15 판정이 「가장 복원되지 않는
자리」라 부른 고유분이 이 두 문장이다.

### 제거 ⑵ — `parseDeleteTarget` doc 534–535 의 뒷절 (−1)

```
// Both sides run it, for the reason parseUpdateTarget sets out above: a refusal
// the operator never had to look at is only reachable ahead of authorize.
```
→ 「Both sides run it, for the reasons parseUpdateTarget and deletePairs set out.」 한 줄. 포인터는 위치만 가리킨다(슬라이스 10 #167 규칙) — 뒷절은
**③ #101 「설계 결정 2 — 인자 검증이 게이트보다 앞선다(`deletePairs()` — `updatePairs()` 선례). 시나리오 10 의 「인자 검증에서 거부됨」이 승인 요청 0건으로
성립한다. 핸들러는 `authorize` 하류라 그 자리로는 불가능하다」** ✅ 축자 + **① `deletePairs` doc**(「for the reason updatePairs states: authorize runs before
the handler, so a call the handler would reject has already cost an approval request by then」)의 압축 사본이라 ⑴ 과 같은 형이다. 09-15 판정(`rct_20260915-0003`)
이 「`parseUpdateTarget` 의 논증을 통째로 다시 적은 9줄을 포인터로 접었다」고 한 그 포인터의 꼬리를 마저 접는 것이고, 가리키는 곳을 `parseUpdateTarget`(함수가
하나인 이유)과 `deletePairs`(게이트 쪽이 먼저인 이유)로 갈라 적어 ⑴ 의 편집 뒤에도 한 홉에 닿게 했다.

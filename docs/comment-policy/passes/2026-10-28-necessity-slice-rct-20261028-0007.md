## 유지 (사유 한 문장)

Go 관례 최소 doc(exported 식별자 첫 문장·패키지 주석)은 사유를 따로 대지 않는다. 아래는 필요성 시험으로 남긴 것이다.

### attach
- `AttachDefaultReadSeconds`/`AttachMaxReadSeconds` — 끝이 없는 스트림을 응답으로 바꾸는 것이 읽기 창이라는 것과, 도구 계층이 같은 값을 쓰도록 export 한 이유(복사본은 어긋난다).
- `attachStdinReader` — 페이로드 뒤 EOF 를 보내면 client-go 가 원격 stdin 을 닫고 API 서버가 attach 종료로 읽어 창이 사라진다는 관측(3.00s 대 0.016s, 빈 stdout 이 성공으로 반환)과, 단위 테스트가 필요해 이름 있는 타입인 이유.
- `AttachResource` 안의 끊긴 스트림 처리·`done` 컨텍스트 수명·창 만료가 정상 종료인 이유 — 지우면 실패/성공 분류와 goroutine 정리를 틀리게 고친다.
- `parseAttachTarget` 의 컨테이너 개수 검사를 일부러 넣지 않은 이유, `command` 인자 거부 이유, 빈 문자열 stdin 을 보존하는 이유.
- `attachPairs` 의 쌍이 `create ⟨pods⟩/attach` 인 이유(하위 리소스를 좌표에 붙인다).
- 테스트: 한 바이트씩 읽는 이유, 페이로드 뒤 읽기가 응답하면 안 되는 이유(결함 전체), 빈 페이로드도 창을 가져야 하는 이유, 승인 화면이 stdin 을 보여야 하는 이유.

### exec
- `streamMaxOutputBytes`(`yes` 는 끝나지 않으므로 바이트 상한이 읽기도 멈춰야 한다)·`execMaxDuration`(명령이 파드에서 더 살 수 있어도 응답이 우선)·`limitedWriter`(전송을 비워야 멈추지 않는다)·`Bytes`(텍스트 판정을 하지 않는 이유)·`streamSubresourceServed`(scale 문구를 재사용하지 않는 이유).
- `ExecResource` 의 두 변형 관계·디스커버리가 답이지 권한이 아니라는 것, 상한이 읽기와 듣기를 함께 멈추는 이유, 쓰기 종료 뒤에만 플래그를 읽는 이유(경합 없음).
- `execStreamOutcome` — 비정상 종료만 `CodeExitError` 로 오고 0 은 침묵이라 성공 경로가 nil 이라는 것, 바이트 상한이 컨텍스트를 취소해 마감이 아닌 취소로 돌아온다는 것, 그때 종료 코드가 미정인 이유, 두 분기 내부 사유.
- `parseExecTarget` 의 컨테이너 개수 검사 부재 이유, `execPairs` 의 쌍.
- 테스트: 컷 뒤 쓰기가 계속 비우는 이유, `Success` 가 영원히 거짓이 되는 결함, 취소가 전송 오류가 아닌 이유, 종료 코드 미정 분기, 상한 플래그 없이는 호출자 이탈과 구분할 수 없다는 것.

### port-forward
- 읽기 창 상수 — 쓰기와 달리 응답 대기는 스스로 끝나지 않는다.
- `PortForwardResource` — 로컬 포트를 열지 않는 이유(프로세스 네임스페이스에 리스너를 들이고 같은 파드의 다른 것이 닿는다).
- `roundTrip` — 에러 스트림을 먼저 만드는 순서 불변식, 쓰기 반쪽을 닫아야 서버가 응답을 시작하는 이유, 에러 스트림에 쓰지 않는 이유, 포트 오류가 에러 스트림으로 온다는 상류 동작, 닫힌 뒤 읽기 오류와 창 만료가 오류가 아닌 이유.
- `newPortForwardOutcome` — 잘못된 UTF-8 이 조용히 바뀌므로 base64 로 싣고 표시한다는 것.
- `parsePortForwardPayload` 의 두 표기와 둘 다 주면 거부하는 이유(정본), 페이로드가 없을 때 배너를 읽는 용례, `portForwardPairs` 의 쌍.
- 테스트: `silent` 데이터 스트림의 쓰임, `fakeStreamConn`/`fakeStream` 의 역할, 상한 테스트가 메모리를 근거로 두는 이유, 승인 화면이 포트·페이로드를 보여야 하는 이유, 거부가 승인 프롬프트를 소모하면 안 되는 이유.

### proxy
- 읽기 창 상수, `ProxyResource` — `rest.Request` 의 `Do`/`Stream` 을 쓰지 못하는 이유(전체 버퍼링 · 비 2xx 를 오류로 바꿈)와 전송 계층을 직접 쓰는 결론, 상한이 읽기도 멈춰야 하는 이유(follow 엔드포인트).
- `ProxyVerbForMethod` 가 한 곳에 있는 이유, `splitProxyPath` 가 `?` 를 이스케이프하지 않게 나누는 이유와 kubelet `/exec` 용례, `apiserverRefusal` 이 403 두 출처를 본문으로 가르는 이유, `newProxyOutcome` 의 인코딩 사유.
- `parseProxyTarget` — 파서가 승인 전에 도는 이유와 kubelet `/exec` 가 승인 화면에 오르면 안 된다는 것, `proxyPairs` 가 동사를 인자에서 뽑는 유일한 자리인 이유, `resourceProxy` 가 경로를 검사하지 않는 것이 의도라는 불변식.
- 테스트: 정규화된 슬래시가 `//` 로 라우팅되지 않는 이유, 모든 메서드가 게이트를 거쳐야 하는 이유(GET 이 읽기 게이트를 통과하는 동사), 확대가 문서 없이 살아남는 경로를 막는 이유, 승인 화면의 kubelet 경로 표시, 잘림 표시가 필요한 이유.

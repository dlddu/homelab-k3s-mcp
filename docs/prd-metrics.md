# PRD: 메트릭 (metrics)

서버의 호출·거부·지연을 **수치로** 관측하는 공통 기반. 감사 기록(`prd-audit-log.md`)이
「무슨 일이 있었는가」를 건별로 답한다면, 이쪽은 「지금 어떤 상태인가」를 집계로 답한다.

## 달성 가치

- **V6: 서버 행위의 감사 가능성** — 거부가 늘고 있는지, 어떤 도구가 느려졌는지를 건별 기록을
  전수 읽지 않고 알게 한다. 특히 **거부율의 급변**은 게이트 오작동·설정 사고의 가장 이른 신호다.
- **V3: 안전한 운영(Safe-by-default)** — 메트릭 노출 경로가 `/mcp`의 인증 경계를 우회하지
  않는다(AC5).
- **V2: 단명·최소권한 자격증명** — 라벨이 민감값을 실어 나르지 않는다(AC4).

## 표면 개요

- **위치**: 서버 공통 기반. 감사 기록과 **같은 지점**에서 파생한다 — 두 곳에서 따로 세면 둘이
  어긋나고, 어긋나면 어느 쪽이 맞는지 판정할 근거가 없다.
- **형식**: Prometheus 텍스트 노출(현행 홈랩 스택이 Mimir/Prometheus 계열이므로).
- **계열 전집**(AC4가 이 표를 닫힌 집합으로 고정한다):

  | 메트릭 | 라벨 | 계열 상한 |
  |--------|------|-----------|
  | `mcp_tool_calls_total` | `tool`, `result` | 등록 도구 수 × 3 |
  | `mcp_tool_refusals_total` | `tool`, `reason` | 등록 도구 수 × 8 |
  | `mcp_tool_duration_seconds` | `tool` | 등록 도구 수 × 버킷 |
  | `mcp_gate_wait_seconds` | `decision` | 6 × 버킷 |

  **셋 다 클러스터 상태가 아니라 서버 코드가 값을 열거한다** — 계열 수가 CRD·네임스페이스·
  리소스 개수에 비례하지 않는 것이 이 설계의 핵심이다.
- **범위 밖**: 대시보드·알림 규칙(관측 스택 쪽), 분산 트레이싱, 감사 기록의 필드 계약
  (`prd-audit-log.md`).

## Acceptance Criteria

### AC1: 도구별 호출 수

- **설명**: `mcp_tool_calls_total{tool, result}` — 도구 이름과 결과(성공·거부·에러)를 라벨로
  갖는 카운터가 모든 도구 호출을 센다. 라벨 둘 다 값이 열거되므로 계열 상한은
  `등록 도구 수 × 3`으로 배포 시점에 확정된다(AC4).
  등록된 도구는 **호출된 적이 없어도** 0으로 노출된다 — 계열이 없는 것과 0인 것이 구별되지
  않으면 「이 도구는 아무도 안 쓴다」와 「이 도구가 계측에서 빠졌다」를 가를 수 없다.
- **달성 가치**: V6
- **검증 방법**: 성공·거부·에러를 각각 일으키고 해당 라벨의 카운터만 1씩 오르는지, 미호출
  도구가 0으로 노출되는지 확인한다.

### AC2: 거부 사유별 카운터

- **설명**: `mcp_tool_refusals_total{tool, reason}` — 거부는 사유별로 갈려 계수된다.
  `reason`은 인증 실패, 입력 검증, 통합 미설정, 그리고 게이트 판정 다섯(승인 거절·만료·
  타임아웃·통신 실패·게이트 미설정)으로 **여덟 값**이며, 게이트 판정은
  `prd-audit-log.md` AC2와 **같은 구분**을 쓴다(자동 승인은 거부가 아니므로 여기 들어가지
  않는다 — 그 관측은 감사 기록의 표기 필드다).
  AC1과 별도 카운터로 두면 **`sum(refusals_total) == calls_total{result="refused"}`** 불변식이
  성립한다. 이 등식이 어긋나면 사유 라벨을 붙이지 않은 거부 경로가 있다는 뜻이므로, 계측
  자신의 누락을 계측이 잡는다. 사유를 뭉치면 사람이 거절한 것과 게이트가
  고장난 것이 같은 선으로 보이는데, 후자는 즉시 조치 대상이고 전자는 정상 동작이다.
- **달성 가치**: V6, V3
- **검증 방법**: 각 사유의 거부를 일으키고 해당 사유 라벨만 오르는지 확인한다.

### AC3: 처리 지연

- **설명**: `mcp_tool_duration_seconds{tool}`으로 처리 지연을, `mcp_gate_wait_seconds{decision}`
  으로 승인 대기를 각각 히스토그램으로 관측한다. 대기 쪽에 `tool`을 붙이지 않는 것은 의도다 —
  기다린 것은 사람이고, 「어느 도구가 오래 기다렸나」는 건별 질문이라 감사 기록이 답한다.
  **게이트 대기 시간을 처리 지연에서 가르는** 이유는 — 사람의 승인을 기다린 시간이 도구 지연에 섞이면 분포가 사람의 응답 습관을
  재는 것이 되고, 실제 처리가 느려졌는지는 보이지 않는다.
- **달성 가치**: V6
- **검증 방법**: 즉답 도구와 게이트를 타는 도구를 각각 호출해 두 계열이 따로 기록되는지,
  승인 대기가 길어져도 처리 계열이 그만큼 커지지 않는지 확인한다.

### AC4: 라벨에 싣지 않는 것

- **설명**: 라벨은 **세 개뿐이다** — `tool`(등록 도구 이름), `result`(성공·거부·에러),
  `reason`(거부 사유). 셋 다 서버 코드가 값을 열거하므로 **배포 시점에 계열 수의 상한이
  확정된다**. 리소스 좌표(`apiVersion`·`kind`·`namespace`·`name`), 주체 식별자, 경로, 명령은
  라벨이 되지 않는다.
- **`kind`를 뺀 것이 이 AC의 판단 지점이다.** 좌표 기반 generic 도구 구조에서 `kind`는
  **유한하지 않다** — CRD가 설치되면 같이 늘고, 그 증가는 이 서버가 통제하지 못한다.
  `kind`를 라벨로 두면 계열 수가 **클러스터의 CRD 개수에 비례**해, 이 AC가 막으려던 카디널리티
  폭발을 이 AC 자신이 열어 두는 꼴이 된다. 선언 목록 + `other`로 접는 방법도 있지만, 그러면
  「선언에 없는 종류」가 전부 한 칸에 뭉쳐 **`other`가 늘었다는 관측이 무엇을 뜻하는지 답할 수
  없다** — 결국 감사 기록을 읽어야 한다. 그럴 바엔 처음부터 감사 기록이 답하게 둔다.
- **종류별 질문은 `prd-audit-log.md`가 답한다** — 「Secret 접근이 늘었나」·「어떤 kind를 많이
  만지나」는 레코드의 대상 필드로 질의한다. **두 표면의 역할 분담이 여기서 갈린다**: 메트릭은
  상한이 확정된 저차원 추세, 감사 기록은 고차원 사후 질의.
- **달성 가치**: V2, V6
- **검증 방법**: 좌표만 다른 호출을 반복했을 때 시계열 수가 늘지 않는지, 노출된 라벨 이름
  집합이 정확히 위 셋인지 확인한다. CRD를 설치한 변형에서도 계열 수가 불변인지 확인한다.

### AC5: 노출 경로와 인증 경계

- **설명**: 메트릭은 `/mcp`와 **다른 경로**로 노출되며, 그 경로가 `/mcp`의 인증을 우회하는
  통로가 되지 않는다 — 메트릭 응답은 AC4의 라벨 집합만 담고 도구 실행·리소스 조회를 수행하지
  않는다. 노출 대상은 클러스터 내부 스크레이퍼이며, 인그레스로 공개하지 않는다. 메트릭
  수집기가 없거나 노출이 꺼져 있어도 서버 기동과 도구 호출은 영향을 받지 않는다.
- **달성 가치**: V3, V6
- **검증 방법**: 메트릭 경로가 인증 없이 도구를 실행하거나 클러스터 리소스를 반환하지 않는지,
  노출이 꺼진 변형에서 서버와 도구가 정상인지 확인한다.
